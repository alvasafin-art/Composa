# Диагностика задержек Composa Studio 17.21

База — `main` на коммите `fde9ab4` (PR #38). Измерения сделаны в Release на Windows x64 с 12 логическими процессорами. Для композитора использован растровый Skia с отключённым OpenCL. Сценарии интерфейса прошли в Avalonia Headless с окном 1440 × 900. Время кадра учитывает обработку ввода и отрисовку холста до конца callback. Физическую задержку пера, GPU-презентацию и показ кадра монитором нужно измерять на обычном окне.

## Исправленные причины

- Смешивание RGB16 для корректирующих слоёв и групп читало ширину и шаг растра через Skia в пиксельном цикле. Теперь размеры и шаг берутся один раз, а пиксели читаются из текущей строки. Измерено на корректирующем слое «Инверсия» с тремя вариантами покрытия. Остальные корректировки и проходные группы используют тот же этап смешивания.
- Кэш эффектов удерживал максимум 12 изображений, даже если стек целиком помещался в его бюджет памяти. На 21 кадр с 16 такими слоями после прогрева пришлось 336 повторных вычислений эффектов, а с 24 слоями — 504. Кэш теперь допускает до 128 записей, сохраняет бюджет 384 МиБ и прежнее исключение для одного результата крупнее бюджета. В обоих сценариях после прогрева повторных вычислений стало 0. В тесте из 8 слоёв кэш и раньше вмещал весь стек.
- Растушёванная маска проходила медленный пересчёт плотности даже при 100%. При меньшей плотности теперь используется таблица для всех 256 значений Alpha8 с прежним округлением. В замере остаётся стоимость самой растушёвки Skia.
- Те же обращения к Skia были в подготовке «Наложения цвета» RGB8/RGB16 и в каждом сэмпле размытия в движении RGB16. Размеры считываются один раз, перед обработкой пикселей.

Стоимость самих отпечатков за ту же фазу составила около 40 мс.

## Кисть 500 px при разных масштабах

Отдельное сравнение с `a0bdd36` в том же PR проверило задержки во время движения и после отпускания. Предпросмотр собирает поступившие до задачи отрисовки изменения и отправляет композитору одну область для обновления. При дробном масштабе полосы отрисовываются в повреждённых столбцах с прежней сеткой сэмплирования. Для целочисленной сетки простых растровых слоёв уменьшаются и временные буферы. Для одного выровненного слоя в масштабе 100% и выше композитор использует пиксели нужной области напрямую, с преобразованием в профиль вывода при необходимости.

После завершения мазка растровые уровни для уменьшенного масштаба копируют ранее рассчитанные пиксели и пересчитывают изменившийся участок. Это работает для RGB8 и RGB16. Если прежнего уровня нет или повреждение охватывает больше половины уровня, он строится обычным способом. Кэш локальных эффектов использует тот же механизм при сохранении той же сетки. Наложение цвета участвует в локальном предпросмотре для поддерживаемых растровых слоёв.

| Сценарий | Медиана до → после, мс |
| --- | ---: |
| Кисть 500 px RGB8, отпускание при «Вписать» | 23,1 → 13,4 |
| Кисть 500 px RGB16, отпускание при «Вписать» | 74,5 → 28,4 |
| Кисть 500 px RGB16, движение при 100% | 6,4 → 5,2 |
| Кисть 500 px, движение при 200% | 7,0 → 6,6 |
| Ластик 500 px, движение при 200% | 6,8 → 6,4 |
| Штамп 500 px, движение при 200% | 7,3 → 7,1 |
| Кисть 500 px, обработка серии входных событий при «Вписать» | 2,4 → 1,3 |
| Точечная восстанавливающая кисть с пятью подложками и стилями, обработка движения при «Вписать» | 4,2 → 0,5 |

Замер обработки ввода заканчивается раньше готовности кадра. При 200% выигрыш движения был небольшим, а у отдельных инструментов p95 варьировался между повторами. При сериях из восьми событий в длинном мазке 500 px число обновлений предпросмотра снизилось с 503 до 80, p95 готовности кадра снизился с 31,6 до 25,8 мс.

На предоставленной фотографии в сценарии из 30 мазков медиана задержки движения снизилась с 8,7 до 6,4 мс, отпускания — с 51,8 до 14,0 мс. Внутри измеренной фазы обновление предпросмотра заняло 104 мс вместо 416 мс, а композиция после мазков — 145 мс вместо 1242 мс. Ретушь, Undo/Redo и повторное открытие дали одинаковые результаты. Хеши растра и контрольных кадров совпали в сценариях `brush8`, `brush16`, `tools`, `brush-preview` и в длинном мазке, включая повтор `tools` при 200%. GPU-презентация и физическая задержка пера в этих прогонах не измерялись.

Для повтора при 200% выполните `Run-CanvasPerformance.ps1` со сценарием `tools` и переменной окружения `COMPOSA_PERF_TOOL_ZOOM=200`.

### Где проверять архитектуру дальше

1. **Кадр и GPU.** Обычный путь `CanvasView.UpdateViewCache → EditorSession.RenderViewportFrame → DocumentRenderer.RenderCpu` готовит буфер синхронно при записи операции отрисовки. CPU ведёт композицию полосами и копирует их в буфер показа. При малой правке вызов холста сегодня не передаёт полный размер стабильной сетки полос. Нужно измерить стабильные тайлы с обработкой ореолов и отменяемую фоновую подготовку кадра, сверяя с итоговым рендером. В приложении GPU-презентация используется при подходящих сценах во время навигации и перемещения ниже 100% для sRGB RGB8. OpenCL-композиция при масштабе 100% работает с ограниченным набором слоёв и режимов и читает результат обратно в CPU. Их покрытие и цену нужно зафиксировать трассировкой в обычном окне с включённым и выключенным GPU.
2. **Warp и увеличенный холст.** Для Warp измерить отдельно приготовление сетки, генерацию растрового представления, маски и композитинг. Текущее отсечение отдельных участков сетки при 100% сохраняет полную выходную поверхность. Для крупных мазков проверить загрузку изменённых участков на GPU и время показа итогового кадра в обычном окне.
3. **Холодные эффекты и фильтры.** Предпросмотр крупного слоя может сначала собрать полноразмерный эффект и лишь затем уменьшить его. Сравнить вычисление на уровне масштаба просмотра и пересчёт только затронутой области с ореолом. Полноразмерный результат и рабочий профиль проверять отдельно.
4. **Другие пиксельные циклы.** В `BlendIfPixels.Apply`, `FilterBlending.Apply` и некоторых ветках `ImageFilters` размеры Skia-растра также читаются внутри обработки пикселей. Поиск по исходникам выявил кандидатов, отдельные замеры нужны для ранжирования. Для режимов смешивания, холодной сборки эффектов и фильтров проверять RGB8 и RGB16 по отдельности.
5. **Взятие образца.** Пипетка на sRGB вызывает `Composite()`. При пустом кэше один образец может вызвать композицию всего документа. Штамп и восстанавливающая кисть в режиме «Все слои» получают отдельный полноразмерный буфер источника при старте мазка. Измерить первый клик отдельно от серий, затем проверить композицию только требуемой области с сохранением точного сэмплирования, ореолов корректировок и исходного профиля.

## Воспроизведение

Подготовка пакетов и моделей описана в [инструкции стенда холста](canvas-replay.txt). Для проверки композитора исходный каталог передаётся явно, поэтому один и тот же стенд можно запустить на любой из двух сборок. Запускайте последовательно из ветки с этим стендом.

```powershell
dotnet run --project scripts/performance/CompositorLatency -c Release -p:CanvasPerformance=true -p:ComposaSourceRoot=C:/bench/composa-main
dotnet run --project scripts/performance/CompositorLatency -c Release -p:CanvasPerformance=true
```

Стенд выводит медиану, p95, счётчик расчётов эффектов и SHA-256 растра. Для измерений окна используйте пять сценариев существующего стенда. Для повторяемой оценки p95 нужны отдельные прогоны каждого сценария. Таблица выше описывает один диагностический проход.

```powershell
pwsh -File scripts/performance/Run-CanvasPerformance.ps1 -DataDirectory C:/bench/composa -Label main -GenerateFixtures -Scenario interaction,tools,card,banner,photo
```
