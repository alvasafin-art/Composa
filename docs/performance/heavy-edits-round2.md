# Раунд 2. Тяжёлые эффекты, деформации и первый образец цвета

База A — `7a71e1cce22e93d78b33eb109c9c57b64b6aa8c2`. В B меняется цикл Blend If в CPU-композиторе. Обе сборки Release с `CanvasPerformance=true`, Windows, Core i5-12400F, 12 логических процессоров. OpenCL композиции и фильтров выключен в стенде. Тест напрямую вызывает Core и измеряет время до возвращения вызова. Интервалы ввода, Skia/Avalonia, DWM и экран сюда не входят. Сравнение выполнено на одном ПК, последовательно A → B и B → A в отдельных процессах.

## Что измеряли

- Warp на слое 3200 × 1920 внутри документа 3840 × 2160. Изменение сетки, новая видимая область при перетаскивании узла, повтор той же области, подтверждение и первый кадр 1056 × 768 в нативном масштабе. В базе уже присутствуют изменения из PR №25/27: `acd9b10` и `1cf51ae` — предки базы. Проверены рабочие пути ограниченного интерактивного разрешения и отсечения частей сетки для видимой области Warp, разреженных тайлов Liquify и ограниченной подготовки Spot Healing.
- Liquify на таком же слое. Отдельно изменение поля, превью 1280 px, подготовка полноразмерного растра и его принятие в историю. Это CPU-работа Core без очереди диалога.
- Синтетическая 4K-композиция из фона, трёх растров с масками, группы, двух стилей Stroke/Shadow, Blend If, маскированной корректировки Invert и маскированного Smart Gaussian Blur. Для предпросмотра выход 1440 × 810, стили сбрасываются перед холодным действием. Тёплый повтор сохраняет кэш стилей. Отдельно измеряются пересчёт Smart Filter и финал 3840 × 2160.
- Первый образец пипетки берётся из новой сессии поверх тех же неизменяемых растров с уже прогретым кэшем стилей. Для второго замера sRGB-сессии заранее строится полный display composite. P3 использует существующее локальное чтение в рабочем профиле в обоих замерах.

## Причина и границы выигрыша

Blend If вызывал свойства `SKBitmap.Width` внутри прохода по пикселям, а для Alpha8-покрытия с float-входами ещё и `RowBytes`. Это обращения к нативному объекту с частотой пиксельного цикла. В B размеры и шаги строк читаются один раз на буфер. Вес каналов, округление, операции с premultiplied alpha, тип и профиль поверхности сохранены. Ускорение распространяется на сцены, где работает CPU-расчёт Blend If. В первом проходе суммарное время всех полос внутри этого расчёта у тёплого 4K-превью RGB8 упало с 3779 до 25 мс на кадр. Это сумма параллельных интервалов. Время кадра по стеночным часам упало с 371 до 19 мс.

Холодный предпросмотр всё ещё тратит сотни миллисекунд на формирование слоёв с эффектами и построение уровней уменьшения. Дополнительная серия B (N=7) дала в среднем 336/410 мс внутри двух холодных эффектов RGB8/RGB16 P3 суммарно. Пересчёт Smart Gaussian отделён от композиции. Для RGB8 выделение выходной поверхности заняло 1,8 мс из 57,3 мс, внутренний вывод и размытие Skia проходят одним вызовом рисования. Для RGB16 подготовка растра заняла 32,5 мс, `FloatGaussian` — 69,7 мс.

В полном рендере RGB16 P3 маскированная корректировка Invert суммарно по параллельным полосам тратила 82 мс на подготовку растра, 124 мс на само преобразование и 360 мс на смешивание. Первый образец sRGB выделял полноразмерный буфер за 2,0/2,8 мс в RGB8/RGB16. CPU-композиция занимала 64/177 мс по стеночным часам, копирование полос в display composite — 6/28 мс суммарно внутри этих параллельных интервалов.

Запись узла Warp в базовом прямом проходе занимала около 0,05–0,74 мс медианы. Повтор уже вычисленного предпросмотра — 3,8/12,0 мс RGB8/RGB16 P3. После подтверждения основной расход приходился на тесселяцию с нативным растрированием, около 225/251 мс на действие в среднем внутри этапа. Для Liquify RGB16 P3 из базовых 7,2 мс медианы полного растра сквозная трасса выделяет в среднем 6,2 мс копирования источника и 1,2 мс ремапа. Принятие готового результата в историю занимало около 0,05–0,06 мс. Разброс на превью Liquify высок, ускорение деформаций в этом раунде не заявляется.

Локальный прототип пипетки рендерил одну исходную полосу. На прогретой сцене первый вызов достигал 28/64 мс p50 в RGB8/RGB16 sRGB. При движении указателя по холсту он снова рендерил бы полосу для каждого запроса. В итоговой сборке первый вызов заполняет кэш, а последующие чтения sRGB занимают доли микросекунды при валидном кэше. Прототип остался в локальной трассе. Режим программного вывода из раунда 1 остаётся в стенде этого раунда.

Все 26 проверяемых результатов стенда, включая цвета и SHA-256 полного растра, совпали в обоих порядках. Отдельный тест сравнивает побайтно частичное обновление и полный рендер на границе повреждения с размытием, масками и группой в RGB8 sRGB, RGB8 P3 и RGB16 P3, затем сравнивает полный рендер после Undo и Redo.

## Воспроизведение

```powershell
dotnet run --project scripts/performance/CompositorLatency -c Release -p:CanvasPerformance=true -- heavy-edits
```

Для A использовался тот же стенд на исходниках `7a71e1c` с одинаковыми диагностическими отметками этапов. Локальные журналы прямого и обратного прохода хранятся в `artifacts/heavy-round2`: `baseline-forward.jsonl`, `final-forward.jsonl`, `final-reverse.jsonl`, `baseline-reverse.jsonl`. `final-stages.jsonl` содержит дополнительное разбиение подготовки и копирования. `candidate-forward.jsonl` содержит локальный прототип пипетки. В синтетических сценах нет файлов пользователя.
