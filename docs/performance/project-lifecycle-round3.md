# Раунд 3. Открытие, запись и память вкладок

При приёмке восстановлен стандартный уровень сжатия CMPS. Вариант B остался диагностическим экспериментом: более быстрая запись увеличивала архивы и замедляла чтение большого recovery-файла в двух наблюдениях. Замеры и стенд сохранены для сравнения.

База — `5d2fc76f9111d70ac31cf58108a3727160a83a61`. Стенд использует обычное окно Win32/Avalonia в Windows RDP, процессор Core i5-12400F, штатный режим вывода и выключенный OpenCL-композитор. Две серии прошли в порядке A → B и B → A в новых процессах. В обратной серии первым открывался большой проект. Файловый кэш Windows не сбрасывался. Изолированный профиль включает штатные миниатюры недавних файлов, восстановление и настройки. Автообновление исключено из замера.

Два проекта созданы из локальной копии `FK_01491_.png`. В каждом есть два растровых слоя, группа, маска, стиль тени и вложенный смарт-объект. Малый — 768 × 512 RGB8 sRGB, 1,40 МиБ. Большой — 3840 × 2160 RGB16 Display P3, 70,63 МиБ. В A и B открывались одни и те же исходные архивы. Сохранение и экспорт шли в отдельные копии.

## Запись CMPS

PNG растров внутри архива кодировались с уровнем zlib 6, который Skia использует по умолчанию. Для первого сохранения большого проекта базовый PNG-кодировщик занимал 4,14–4,16 с. Запись подготовленных записей в ZIP вместе с включением ICC занимала 92–104 мс. Остаток включает запись манифеста и завершение архива. Это замеры файловых вызовов приложения с кэшем ОС. Отдельный физический flush диска не измерялся.

В B для цветных растров задан zlib 1. Skia выбирает из того же набора фильтров строк PNG. Цветовая глубина, PNG, ICC, ZIP, манифест и порядок атомарной замены прежние. Растры по-прежнему кодируются при каждом сохранении. Изменение действует в ручной и автоматической записи CMPS. Маски, отдельный экспорт PNG и PSD используют свои прежние кодировщики.

В таблице p50 / p95 в миллисекундах. При N=3 p95 — максимум серии. Для первого сохранения указан одиночный замер в каждой серии.

| Сценарий | N на сборку | A → B | Повтор B → A, столбцы A → B |
| --- | ---: | ---: | ---: |
| Малый, первое сохранение | 1 | 175 → 104 | 158 → 71 |
| Малый, повтор после переименования слоя | 3 | 162 / 179 → 58 / 60 | 146 / 157 → 60 / 70 |
| Малый, автосохранение | 3 | 147 / 493 → 53 / 59 | 140 / 141 → 55 / 58 |
| Большой, первое сохранение | 1 | 4302 → 2494 | 4306 → 2533 |
| Большой, повтор после переименования слоя | 3 | 4189 / 4226 → 2419 / 2468 | 4183 / 4203 → 2382 / 2550 |
| Большой, автосохранение | 3 | 4164 / 4198 → 2460 / 2651 | 4187 / 4365 → 2390 / 2396 |

Архивы обеих сцен выросли приблизительно на 4,4%. Большой — с 70,63 до 73,76 МиБ. Повторное чтение большого recovery-файла, записанного B, заняло 1,43–1,50 с против 1,37 с в A, по одному замеру на серию. Извлечение записей отличалось слабо (21,6–21,9 мс в A и 22,6–23,3 мс в B). Основное различие пришлось на PNG-декодирование. Наблюдений пока мало для обобщения. В ручном сохранении большого проекта повторный вызов возвращал UI-поток за 0,2–0,4 мс, после чего работал фоновый записывающий поток. p95 интервала диспетчерского таймера обычно был около 16 мс.

Микрозамер кодировщика для основного слоя сравнивал уровни 1, 2, 3 и 6 и два набора фильтров. Уровень 1 со всеми фильтрами снизил p50 4K PNG с 2484–2501 до 1355 мс при росте PNG около 4,7%. Ограничение фильтров до Sub/Up было ещё быстрее, но дало более крупный файл. SHA-256 декодированного растра совпал для всех вариантов. Для малого RGB8 растра p50 упал с 81–89 до 30 мс.

## Открытие, экспорт и переключение вкладок

- Холодный запуск до возврата `Window.Show` занял 2,19–3,16 с за четыре процесса. Измерение начинается в `Main` стенда и включает подготовку тестового профиля. От этого старта первый кадр малого проекта закончился за 3,47–3,93 с, большого — за 5,06–5,24 с. Это завершение отрисовки холста Skia. Подтверждённой метки DXGI/DWM Present у стенда нет.
- Первый большой проект внутри процесса открывался до возврата `OpenPath` примерно за 1,7–2,2 с. От запроса до завершения первого кадра проходило 2,44–2,98 с. Извлечение PNG из контейнера занимало 24–27 мс, PNG-декодирование 1,52–1,63 с, построение вложенного предпросмотра 9–30 мс. Первая десериализация манифеста за процесс занимала 230–259 мс в обеих очередностях файлов. Следующие укладывались примерно в 1 мс.
- Тёплое повторное открытие того же файла давало p50 1,58–1,64 с до кадра у большого проекта и 70–94 мс у малого. Готовая вкладка переключалась за 62–68 мс p50 у малого и 63–93 мс у большого по 7 переключениям. `SetSession` в синхронной части занимал обычно 41–55 мс, из них установка моделей панелей в тёплом проходе около 2–6 мс. Сигнал UI — интервал между срабатываниями таймера диспетчера, а не задержка указателя. При холодном открытии большого проекта максимальный интервал 0,80–1,14 с, при повторном открытии p50 максимума 0,25–0,26 с.
- Фоновая миниатюра недавних файлов при первом открытии большого проекта заняла 0,63–0,79 с. Её интервал пересекается с первым рендером холста. Время этих двух работ нельзя складывать. При повторе готовая миниатюра обслуживалась из кэша по времени изменения файла.
- Экспорт большого PNG занимал 2,64–3,17 с. Полное сведение — 95–101 мс, остальное — кодирование и запись в файловый поток. Стенд вызывает те же операции flatten/save без диалога выбора файла. Сопоставимое ускорение экспорта не подтвердилось.

## Память и контроль результата

- Windows Private Working Set считывался каждые 15 мс через `PROCESS_MEMORY_COUNTERS_EX2`. Управляемые аллокации — разность process-wide `GC.GetTotalAllocatedBytes` начала и конца этапа. Холодное открытие большого проекта достигало 605–617 МиБ private WS и выделяло 15–27 МиБ управляемой памяти. Первое сохранение большого проекта держалось около 548–550 МиБ private WS, с 0,8–1,0 МиБ аллокаций. Выигрыша по памяти от уровня сжатия не наблюдалось.
- Пик экспорта большого PNG достигал 842–860 МиБ private WS и около 220 МиБ управляемых аллокаций. После восьми закрытий за процесс, включая три цикла повторного открытия двух вкладок, через 1,5 с после последней контрольной точки private WS был 303–318 МиБ. Управляемая память по `GC.GetTotalMemory(false)` оставалась 171–172 МиБ. Одна из восьми слабых ссылок на сессию ещё находилась в памяти во всех проходах. Эти точки измерения включают экспорт и не доказывают утечку вкладок.
- В штатном headless-сценарии `tabs` пять раз открыли большой проект, сделали мазок и закрыли вкладку. Через 30 с исчезли все слабые ссылки на её растры и все отображения растров в память. Осталась одна из пяти слабых ссылок на оболочку сессии. В этом стенде измеряется private commit, который снизился с 949 до 311 МиБ после ожидания. Private WS измерялся в отдельном нативном сценарии выше.
- Новый архив открыт декодировщиком из `5d2fc76`. Для обоих проектов побайтно совпали декодированные растры, маски, вложенное содержимое, итоговый полноразмерный рендер и ICC. Проверки `RecoveryTests` и `SavingTests` покрывают восстановление, ревизии изменённости и ожидание записи при закрытии.

## Воспроизведение

```powershell
dotnet build scripts/performance/BrushLatency -c Release -p:CanvasPerformance=true -o artifacts/project-round3/bench
$runner = 'artifacts/project-round3/bench/Composa.App.Tests.dll'
dotnet $runner project-fixtures artifacts/project-round3/fixtures 'C:\path\to\photo.png'
dotnet $runner projects artifacts/project-round3/fixtures artifacts/project-round3/result-card.json card
dotnet $runner projects artifacts/project-round3/fixtures artifacts/project-round3/result-banner.json banner
```

Бинарник A собран до смены уровня zlib с теми же отметками фаз. Локальные исходные замеры находятся в `artifacts/project-round3` в файлах `baseline-*-first.json`, `candidate-*-first.json`, `png-options.tsv`, `existing-tabs.json` и `verify-*-baseline-reader.txt`. Фотография, проекты и копии остаются локальными. Определение private working set приведено в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2).
