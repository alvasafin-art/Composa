# Раунд 4. Автоматизация серии редактируемых карточек

## Приёмка CMPS

Коммит `7abe258b5af65ecd76e8a6fce6828a80b397860c` вернул стандартное сжатие цветных PNG внутри CMPS. Отметки стенда и результаты опыта с быстрым сжатием остались. На копиях малого RGB8 и большого RGB16/P3 проекта проверены запись и повторное чтение. В каждом архиве все четыре PNG-записи совпали по длине и CRC с прежним кодеком. Совпали декодированные растры, маска, структура, содержимое смарт-объекта, итоговый рендер и ICC. [Результаты эксперимента со сжатием](project-lifecycle-round3.md)

## Рабочий процесс

Стенд использует те же нативные инструменты и проверки редактируемых слоёв, что `AgentAcceptanceTests`. Два синтетических варианта карточки 3200 × 2000 меняют живой заголовок, заменяют растровый слой Hero и меняют цвет и непрозрачность 20 живых фигур. Каждый вариант запускается на свежей сессии от одного шаблона. Каждый маршрут отдаёт редактируемый `.cmps` и плоский PNG. Для проверки сделаны одинаковые три запроса MCP `render` на вариант, включая отдельный тёплый контроль.

| Маршрут | Вызовы инструментов на вариант | Отрисовки холста | Инвалидации |
| --- | ---: | ---: | ---: |
| Поштучные команды нативных инструментов | 49 | 46 | 44 |
| `batch_set_layers` для фигур, остальные команды те же | 10 | 7 | 44 |
| Один Jint-сценарий на вариант, включая PNG-экспорт | 4 | 1 | 44 |

Это исполнение локального кода инструментов Assistant/MCP и их диспетчеризация в Avalonia Headless. Внешний JSON-RPC-транспорт, токены и циклы реального агента отсутствуют в таймингах. Таймер рендера вызывается после каждой редактирующей команды, поэтому число отрисовок показывает работу при последовательных запросах с возможностью отрисовать промежуточное состояние. Для двух нативных маршрутов стенд создаёт внешнюю транзакцию, аналогичную транзакции Assistant. У Jint транзакцию ведёт сам runtime. Обычные независимые запросы MCP коммитятся по отдельности. Сам `batch_set_layers` группирует свой набор слоёв в одну запись истории.

Ручных действий между вариантами в стенде ноль после одного запуска. В Script Editor без оркестратора для этой серии потребовалось бы два запуска скрипта, по одному на вариант. Физический ручной сценарий мышью не измерялся.

## Сравнение времени

В ячейках p50 / p95 для серии из двух карточек в секундах. N=3 серии в каждом маршруте и порядке, p95 — максимум серии. В каждом процессе меняется порядок маршрутов. Время складывается из двух полных вариантов с их приготовлением сессии, запросами, превью, PNG и CMPS. Однократное изготовление исходников и проверки после публикации вынесены за пределы таблицы.

| Маршрут | A, прямой | B, прямой | B, обратный | A, обратный |
| --- | ---: | ---: | ---: | ---: |
| Поштучно | 3,91 / 4,75 | 3,91 / 4,69 | 3,97 / 4,19 | 3,89 / 3,97 |
| Нативный батч | 3,44 / 3,64 | 3,46 / 3,60 | 3,54 / 3,79 | 3,50 / 3,87 |
| Jint | 3,34 / 3,80 | 3,32 / 3,85 | 3,60 / 4,23 | 3,47 / 4,23 |

Переход на батч уменьшил медиану серии примерно на 10–12%, на Jint — на 9–15%. В обратном порядке Jint запускается первым и получает более дорогой старт. На B в основной части одного варианта медиана поштучных вызовов с отрисовками составляла 358–401 мс, нативного батча — 116–120 мс. Применение внутри Jint занимало 73–76 мс по медиане, без PNG-экспорта. В серии остаётся примерно по 0,7 с на PNG и 0,7–0,8 с на CMPS для каждого варианта.

## Узкие места

Подготовка синтетических входов и запись шаблона занимали 1,28–1,34 с в трёх процессах. У B в прямом проходе один выброс 13,33 с без разбиения на внутренние этапы. Загрузка шаблона занимала 0,16–0,17 с во всех процессах. После загрузки каждый вариант получает собственную копию структуры. При поштучной обработке основная разница видна в применении команд и отрисовке. В тёплых вызовах время до входа в UI-диспетчер в сумме обычно меньше 1 мс на вариант. Сведение и файловый экспорт остаются на всех маршрутах, как и кодирование неизменённых растров при записи CMPS.

Малый `render` MCP (384 px) сначала вызывал полноразмерный `Composite()`. В этой сцене на холодном кэше он занимал примерно 7–16 мс, resize — около 10–12 мс, PNG — около 19–23 мс. На тёплом кэше время `Composite()` было почти нулевым, resize и PNG остались. Отдельный зонд вызвал штатную последовательность AssistantWindow `Composite()` → `AssistantFile.Preview`, 1024 px. Она занимает примерно 90 мс на этой сцене, внутри примерно 9 мс приходится на `Composite()` в первом контрольном проходе. Качество и геометрия этих превью сохранены.

## Изменение экспорта

`ImageFiles.Save` для PNG пишет тот же PNG из нативного буфера Skia во временный файл через существующую вставку метаданных. Прежний путь копировал полный PNG в массив, наращивал второй буфер с метаданными и выделял ещё один массив на выходе. Для PNG около 17 МиБ управляемые аллокации экспорта нативного батча снизились с 76,51 до 0,12 МиБ по p50 в первом направлении и с 76,50 до 0,13 МиБ в обратном. Время p50/p95 было 686/757 → 696/727 мс и 702/723 → 684/790 мс, N=6. Устойчивой разницы по времени PNG-записи нет. Экспорт и запись CMPS по-прежнему упираются в кодировщик. Экспорт заменяет целевой файл после проверки отмены, как и раньше. Сигнал отмены из Jint теперь доходит до этого вызова даже при возврате AI-провайдера без исключения.

## AI-зонд

В каждом процессе один `ai.imageEdit` через реальный `AiTaskService` дошёл до штатного тестового `AiVariantsTests.Connection` в памяти. Источник и PNG для ответа синтетические. В четырёх проходах подготовка входов заняла 7,9–9,2 мс, вызов загрузки с локальным кодированием PNG — 4,0–4,3 мс, отправка графа и немедленный ответ заглушки — 1,6–1,8 мс, декодирование ответа — 2,8–3,2 мс, применение — около 3,3 мс. Весь вызов Jint с настройкой задачи занял 100–110 мс. В заглушке нет очереди сервера, реального переноса по сети и инференса. Эти числа описывают расходы Composa.

## Изоляция и повтор

Во всех маршрутах проверены один Undo, Redo, живая структура документа после повторной загрузки и побайтно одинаковые PNG. Во всех четырёх проходах для каждого варианта совпали все 38 PNG, включая отсоединённые: одинаковый SHA-256 внутри варианта. Проверены сбой скрипта и отмена после постановки AI-команды с откатом локального изменения и сохранением существующего файла при отмене. Отдельный проход вызывает `JavaScriptRuntime` на сессии, не присоединённой к окну. Он последовательно создаёт свежую сессию для каждого варианта, использует один `ExportedPath`, сохраняет согласованный снапшот, а затем публикует оба файла переименованием временного каталога. Такой вариант занимал 1,45–1,52 с. Повтор проверяет существующие PNG и CMPS за 141–145 мс и пропускает уже готовый вариант. Несовпадение является ошибкой. Сопоставление делается по PNG SHA-256, живым свойствам и SHA-256 растров.

Детерминированные правки уже выполняются Jint и нативным батчем. В поставке пока нет отдельной безоконной команды серии, очереди с состояниями заданий и безопасного механизма возобновления произвольных скриптов пользователя. MCP мост подключается к приложению. Jint возвращает один `ExportedPath` на выполнение, ставит AI в очередь перед экспортом и требует внешнего хоста для серии и для сохранения редактируемого CMPS. Отсоединённый прогон стенда проверяет эти границы на синтетическом шаблоне.

```powershell
dotnet build tests/Composa.App.Tests -c Release -p:CanvasPerformance=true
$env:COMPOSA_AUTOMATION_REPLAY = Join-Path $PWD 'artifacts/automation-round4/new-replay'
dotnet tests/Composa.App.Tests/bin/Release/net10.0/Composa.App.Tests.dll -class '*AutomationWorkflowBench' -nocolor

Локальные данные находятся в `artifacts/automation-round4`, файлы `a-forward/report.json`, `b-forward/report.json`, `b-reverse/report.json` и `a-reverse/report.json`. A собран после возврата штатного сжатия и до изменения PNG-записи. Оба бинарника Release с `CanvasPerformance=true`, Windows, Core i5-12400F. OpenCL выключен. Входы для серии и AI-зонда синтетические.
